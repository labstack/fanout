Fanout is configured from the environment, or from a YAML file using the same
keys. Every setting is listed under [Settings](/reference/settings/server),
grouped by the part of the product it belongs to.

Those pages are generated from `internal/config` by `cmd/fanout-docgen`, and
the root `.env`, `.env.production`, and `.env.example` are generated from the
same schema. `just check` fails
when a committed page or template no longer matches the type the loader
binds. That is the whole point of generating them: the reference cannot describe
a setting the binary does not accept, and cannot omit one it does.

## Where a value comes from

A nonempty recognized environment variable wins over the YAML file, and the file
wins over the built-in default. Empty environment values mean no override.
All settings are read once at startup and require restart. Fanout does not load
dotenv files itself. The generated `.env.example` documents types, defaults,
and empty credential placeholders; `.env` and `.env.production` omit secret fields.

For a source checkout, build the binary and use `just run` for local development
or `just run-production` for an explicit production launch. Local order is
`.env`, optional ignored `.env.local`, then injected environment values.
Production order is `.env`, required `.env.production`, then injected values;
personal files are excluded. The Node launcher uses the native dotenv parser
without shell execution or variable interpolation. Missing required files,
unknown names, and secret entries in ordinary dotenv files fail before launch.

Inject credentials from a private selected SOPS profile or the deployment's
secret service. This public repository ships no operator secrets or recipients.
Dotenv values are injected as environment, so nonempty values override the
corresponding `--config` YAML. Launch the binary directly for YAML-only ordinary
configuration.

## Naming

Custom environment settings use the `FANOUT_` prefix. Provider keys and endpoints
use `ANTHROPIC_API_KEY`, `ANTHROPIC_BASE_URL`, `OPENAI_API_KEY`, and
`OPENAI_BASE_URL`. The YAML key is the dotted path in the first column of each
settings table — `storage.duckdb.memory` maps to `FANOUT_DUCKDB_MEMORY`.
Provider settings map to native structured keys under `ai.anthropic` or `ai.openai`.

`FANOUT_AI_PROVIDER` selects the provider and `FANOUT_AI_MODEL` selects its model.
Only the selected provider's key and endpoint are used. Without that key, chat is
disabled. Other vendor/tool settings, including `ANTHROPIC_MODEL` and
`OPENAI_MODEL`, are ignored. See [AI settings](/reference/settings/ai) for
the different base URL meanings and [upgrade instructions](/start/install#ai-configuration-upgrades)
for migrating the retired generic key and base URL settings.

## An unknown variable is an error

Fanout rejects an unrecognised `FANOUT_`-prefixed variable at startup rather
than ignoring it. This matters more than it looks: Fanout is pre-release and
settings get renamed without aliases, so the alternative is a variable you
believe is in effect, silently replaced by a default nobody chose, discovered
months later. A refusal to start is the version of that failure you can act on.

The consequence is that upgrading can require a configuration change, and the
process tells you which one at the first boot after the upgrade.

## Secrets

Settings marked `secret` are redacted from the startup configuration log. They
are ordinary environment variables otherwise: anything that can read the process
environment can read them. Fanout does not encrypt them at rest and does not
integrate with a secret manager — mount them the way you would for any other
process.

## Validation

The whole configuration is validated before any listener opens, so a value the
binary will not accept stops it at startup. [First boot](/start/first-boot)
lists what is checked.
