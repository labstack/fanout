Fanout validates configuration before opening data files or listeners. Invalid
settings stop startup with an error naming the setting. See
[configuration](/docs/reference/configuration) for precedence, secret files and validation.

Local sign-in requires `FANOUT_AUTH_CODE_SECRET` with at least 32 characters.
SMTP and an AI provider are optional; each validates its required settings when
enabled. OIDC requires an HTTPS issuer and public URL, a client ID and a client
secret. The generated [settings reference](/docs/reference/configuration/auth) lists the
available authentication settings.

## Claiming the first administrator

When the control database holds no users, Fanout prints a one-time setup URL to
standard error:

```text
============================================================
 FANOUT SETUP

 Open:  http://127.0.0.1:7520/login?setup_token=…
 Valid: one-time use, expires in 1 hour
 Note:  this URL disappears after the first admin is created
 Warn:  it contains an administrator credential — this output may
        persist in container logs, log aggregators, and scrollback
============================================================
```

Under Docker, read it back with:

```sh
docker logs fanout 2>&1 | grep -A8 "FANOUT SETUP"
```

Open the URL, create the administrator, and **save the ingest token shown after
setup**. The raw token is displayed once; Fanout stores only its hash and cannot
show it again.

An administrator can issue a replacement in **Connect telemetry → Ingest token** in the account menu, or
with `POST /api/settings/ingest/token/rotate`. Save the new token when it is
shown. Rotation invalidates the old token immediately and cuts off existing
exporters until you update their credentials.

The setup form sends `email`, `display_name`, and `setup_token` to
`POST /api/auth/setup`. The first administrator starts with status `active`.

The setup URL is an administrator credential. Restrict access to process logs
until it is consumed or expires. Treat a leaked setup URL as a compromised
installation and rebuild with a fresh data directory before repeating setup.

## Naming the first administrator instead

Set `FANOUT_FIRST_ADMIN_EMAIL` to skip the setup URL. When the control database
holds no users at startup, Fanout creates that address as an active
administrator and prints no setup banner, so no administrator credential reaches
the logs:

```sh
docker run --name fanout --restart unless-stopped -p 7520:7520 \
  -v fanout-data:/var/lib/fanout/data \
  -e FANOUT_AUTH_CODE_SECRET=$(openssl rand -hex 32) \
  -e FANOUT_FIRST_ADMIN_EMAIL=admin@example.com \
  labstack/fanout:latest
```

Fanout validates the address when it loads configuration and stops with an
error if it is malformed. The setting takes effect only on first start with an
empty database. The account it creates is a regular, permanent administrator,
and changing or removing the setting later has no effect on it:

- Once any user exists, it creates nothing. Restarting with the same address is
  a no-op. A different address is refused with a warning naming it, and no
  account is created; an administrator adds further accounts with `POST /api/users`.
- It never promotes, reactivates or edits an existing account. If the address
  belongs to an account that is not an active administrator, Fanout warns and
  leaves the account unchanged.

The first administrator signs in like any other user: with an email code when
SMTP is configured, or with `fanout login-link` as shown below. In OIDC mode
they sign in through the provider, and Fanout links the first sign-in to the account
by its email address, subject to the usual allowed group and domain checks.

:::caution[Claim the administrator account promptly]
Until the first administrator signs in, whoever first proves control of that address
claims the administrator account: anyone who can read its mailbox in local mode,
or any identity provider account that asserts that email in OIDC mode. Use an
address you control, sign in promptly after first boot, and in OIDC mode confirm
that the account's `identity.linked` audit event came from your own sign-in.
:::

No setup request runs, so no ingest token is issued at first boot and ingest
rejects every exporter until the first administrator issues one. After signing in, open
**Connect telemetry → Ingest token** in the account menu and choose
**Issue token**, or call `POST /api/settings/ingest/token/rotate`. Save the token
when it is shown.

## Signing in afterwards

Local mode has no passwords. Once SMTP is configured, active users receive
short-lived codes by email. Without SMTP, run `fanout login-link <email>` with
the server's environment and data directory to mint a 15-minute, single-use
link for an existing active user. For Docker, use:

```sh
docker exec fanout fanout login-link admin@example.com
```

OIDC deployments use the provider's flow instead.
