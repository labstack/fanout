## Unreleased — Pitot rename (2026-11-11)

The product is now **Pitot** (pronounced **PEE-toh**) at
[pitot.dev](https://pitot.dev). The owner approved this rename on 2026-11-11 to avoid a
conflict with a third party's registered US trademark in cloud services.

- The Go module is `github.com/labstack/pitot`; the binary is `pitot` and native
  archives are `pitot_<version>_<os>_<arch>.tar.gz`, containing `./pitot`.
- Container images are `ghcr.io/labstack/pitot` and `docker.io/labstack/pitot`.
  Update deployment manifests, service names, install URLs and MCP client entries.
  The MCP Registry identity is `io.github.labstack/pitot`.
- Configure the server and installer with `PITOT_*` environment variables.
- The query language is now **PitotQL**. Existing structured dashboard queries,
  MCP `query_telemetry` arguments (`text`, `panel.query`, `panel.sql`), query
  keywords, Explore URL parameters and browser storage keys are unchanged.
  Previous query HTTP paths, MCP reference URI and error-code reader aliases
  are removed. Clients must use canonical PitotQL names.
- The control database is `control/pitot.sqlite`; startup opens only this name.
- Telemetry spill footer keys use `pitot.spill.`. Batches with previous spill
  keys fail verification and must be replaced before use.
- Sessions use the `pitot_session` cookie (with the `__Host-` prefix over HTTPS),
  so users must sign in again. Keyboard shortcut preferences reset. Saved chat
  activities using the previous MCP App URI no longer render; begin a new chat.
  Reserved diagnostic context metadata now uses `_pitot_diagnostic_context`;
  discard pre-rename chat history before resuming chat.
- Existing ingest and OAuth secrets and their token prefixes remain valid.
  The image defaults to `/var/lib/pitot/data`: mount the existing volume there, or set `PITOT_DATA_DIR`
  to its existing mount location.
- HTTP request headers and metrics use the Pitot name. Update custom clients
  using the product request header to `Pitot-Request` (and dashboard deletion confirmation to
  `Pitot-Confirm-Delete`), and update Prometheus
  queries and alert rules from the old metric prefix to `pitot_`.

Take a cold backup before upgrading, stop the old service, replace the binary or
image, and start the new service against the same data and secrets. Verify
`/readyz`, sign-in, ingest and a representative query before resuming traffic.



## Release channels

Pitot versions are CalVer tags, `vYYYY.M.N` with an optional maturity suffix.
`N` counts every release in the month, whatever its suffix. Container image
tags omit the leading `v`: release `v2026.9.5` is image tag `2026.9.5`.

| Tag | Channel | Example |
|---|---|---|
| No suffix | Stable | `v2026.9.5` |
| `-rc` | Prerelease: release candidate | `v2026.9.4-rc` |
| `-beta` | Prerelease | `v2026.9.2-beta` |
| `-alpha` | Prerelease | `v2026.9.0-alpha` |

The tag of each
[GitHub Release](https://github.com/labstack/pitot/releases) shows its channel.

Every release, stable or prerelease, is a full GitHub Release with the same
contents: Linux and macOS archives for amd64 and arm64, a `SHA256SUMS` file,
GitHub build-provenance attestations for each archive and for `SHA256SUMS`, and
a multi-architecture image on GHCR with a Docker Hub mirror of the same digest.
[Releases](https://github.com/labstack/pitot/blob/main/docs/release.md#consumer-verification)
shows how to verify them. Fix a problem in a published version with a new
release number, never by replacing that version. A version's image tag can
still be pushed again, so record the digest you deploy and compare it with the
one published for the release.

The `latest` image tag and the installer's default follow the newest release
of either channel. They are not a stable channel. To run stable releases only,
pin a release tag without a suffix (image tag `2026.9.5` for `v2026.9.5`), or
the image digest it resolves to, and upgrade deliberately.

## Read the upgrade notes

Each GitHub Release starts with an **Upgrade notes** section. The release
workflow writes it by comparing the tag with the previous published release.
A tag whose release workflow failed has no release and is skipped, so its
changes are reported by the next published release:

- **Format change: batch format X to Y** (a caution callout) marks a release
  that cannot read telemetry written by earlier releases. Follow
  [when a release changes the batch format](#when-a-release-changes-the-batch-format).
- **Control schema migration** lists the control database migrations the
  release adds. They run forward at startup, so rolling back means restoring a
  backup.
- **Storage** states that the batch format is unchanged and no migrations were
  added, so a missing marker is never ambiguous.
- **Breaking changes** lists the merged changes whose titles carry the
  Conventional Commits `!` marker, for example `feat(auth)!:`.

Maintainers add any manual steps below these markers. The markers compare each
release only with the one before it. When you skip releases, read the notes of
every release between your version and the target.

A release without a generated section predates it. Its notes are
handwritten; read them for the same changes. For example,
[v2026.11.0-alpha](https://github.com/labstack/pitot/releases/tag/v2026.11.0-alpha)
changes the batch format from 4 to 5.

## Breaking changes and notice

A breaking change is one that needs action from an operator or client after
upgrading. That includes removing or renaming an HTTP route, a JSON field or
query parameter, an MCP tool or its arguments, or a configuration variable;
changing a credential format; and changing the batch format.

- **Prereleases** may ship a breaking change in any release, without notice.
  The release's upgrade notes mark it.
- **Stable releases** announce a breaking change in the notes of an earlier
  stable release at least 30 days before a stable release ships it. The
  announcement names what changes, its replacement, and the earliest release
  that may change it.

Additions are not breaking: new routes, tools, optional fields and settings
can appear in any release.

## Route and API deprecation

Pitot does not serve an old and a new name side by side. A rename or removal
changes the route registration, its clients, its authorization and the
generated [HTTP routes](/docs/reference/api) and [MCP tools](/docs/reference/mcp)
reference in one release, with no alias or fallback.

Deprecation is therefore a notice, not a transition period:

1. A stable release's upgrade notes announce the deprecated route, field, tool
   or setting, with its replacement and the earliest release that removes it.
2. Until that release, the deprecated contract keeps working unchanged.
3. The removing release lists the change under **Breaking changes**.

Protocol-defined contracts follow their own specifications rather than this
schedule: OTLP ingest, the MCP protocol, OAuth and the `/.well-known` metadata
paths. Product CalVer never appears in API paths or MCP tool names.

## Upgrade an instance

1. Read the target [GitHub Release](https://github.com/labstack/pitot/releases)
   and every release you are skipping, and pin the target's binary or image
   tag.
2. Take and verify a [cold backup](/docs/guides/backup-and-restore). Record the
   running version with it.
3. Stop Pitot and wait for it to exit.
4. Replace the binary or image. Keep the data directory unless the release
   requires the format-change procedure below.
5. Start Pitot. Check `/readyz`, sign-in, configured OTLP transports and
   representative queries.

Pending control SQLite migrations run forward, in order, at startup, so one
upgrade can cross several releases. Migrations have no down path. A rollback
after migration is not assumed safe.

## Roll back or restore

Restore a backup only with **the version that created it**. Pitot does not
record which release wrote a data directory, so it cannot warn about a
mismatch:

- A release reads only its own batch format and refuses to start on any other.
- An earlier release is not designed to run against a control database that a
  later release migrated.

To roll back, stop Pitot, restore the complete pre-upgrade backup, and start
the previous binary or image. To move to a newer version after a restore,
verify the restored instance first, then upgrade with the steps above. See
[back up and restore](/docs/guides/backup-and-restore).

## When a release changes the batch format

[v2026.11.0-alpha](https://github.com/labstack/pitot/releases/tag/v2026.11.0-alpha)
requires batch format 5 and cannot read format 4. For that upgrade, and any
release whose notes carry a **Format change** marker:

1. Stop Pitot and take a complete cold backup.
2. Move `telemetry/` and `query/` out of the data directory. Keep them together
   for recovery with the previous version.
3. Keep `control/` in place. It preserves users, dashboards, alert rules and
   the ingest token.
4. Install the target binary or image and start Pitot with the same data
   directory setting.
5. Verify readiness and sign-in, then send new telemetry and check a query.

Old telemetry is unavailable in the upgraded instance. Query state rebuilds
from the new telemetry. Do not copy unsupported batches back into it.
See [storage](/docs/concepts/storage) for the current format contract.

v2026.11.0-alpha also renames API and MCP contracts without aliases. Update
scripts and clients using the release notes and [HTTP routes](/docs/reference/api).

## When a release changes credential formats

Ingest tokens use the `foi_` prefix. Pitot rejects tokens issued with the
earlier `fo_` prefix. After upgrading, an administrator creates a token in
**Connect telemetry → Ingest tokens** and updates every collector. Unused login
links issued before the upgrade stop working; request a new one. Connected MCP
agents keep their OAuth tokens.

## Moving to named ingest tokens

The single stored ingest token becomes a token named `default` with its digest
unchanged, so running Collectors keep working. `POST /api/settings/ingest/token/rotate`
is removed; rotate by creating a token with `POST /api/settings/ingest/tokens` and
revoking the old one with `POST /api/settings/ingest/tokens/{id}/revoke`.
`PITOT_INGEST_TOKEN` applies only when no token has ever existed, so leaving it set
is harmless and it cannot restore a revoked token.
